# Multimodal Disease Progression Prototype 2

I started this project to try combining different types of health-related information in one model. This version brings together simulated image features, wearable summaries and clinical values. I wrote it in Python and used PyTorch for the neural network.

The work is still at the prototype stage. The data is generated by the code; there are no real patient records, medical scans or wearable-device files here. I wanted to get the basic pipeline working first, so that I could test how the data is prepared, how the model combines the feature groups and how the predictions are checked.

This is a separate repository from `multimodal-disease-progression-demo` and PACA++.

## What goes into the model

The script creates 240 synthetic patients by default. Each patient has between two and four visits. The gaps between visits are selected as 3, 6, 9 or 12 months.

Each visit has 20 input values:

| Data group | Values | Details |
|---|---:|---|
| Image-derived features | 8 | Simulated numbers; the script does not read an image |
| Wearable summaries | 6 | Simulated numerical values |
| Clinical values | 4 | Scaled age, a binary sex field and two simulated lab values |
| Missingness indicators | 2 | Flags for missing image and wearable data |
| **Total** | **20** | |

Some of the clinical values are also set to missing. When the image or wearable group is missing, its values are set to missing and the corresponding flag is recorded.

The script assigns each visit a stage from 0 to 3. These labels are made for this experiment. They are not taken from a medical staging system and should not be interpreted as real disease severity.

## How the model works

I used a small feed-forward neural network with a separate encoder for each of the three feature groups. The encoded outputs are joined in a fusion layer. The network then has two output heads:

- The main head predicts the stage at the patient's next recorded visit.
- The auxiliary head predicts the stage at the current visit during training.

For each example, the current visit's 20 values are the input and the next recorded visit's stage is the target. The current stage is kept as a training target; it is not part of the input features.

The visit gaps vary, but the model is not given the elapsed time between visits. It also does not look at a sequence of earlier visits. It makes each prediction from one visit's feature values. So the task is next-observed-visit classification, not a prediction at a fixed six- or twelve-month point.

There is no CNN or scan-processing model in this version. The image branch works with eight generated numbers, not actual medical images.

## Languages and libraries

These are the tools used in the current code:

- **Python 3.11** for the application and experiment code.
- **PyTorch** for the neural network, training and saved model weights.
- **NumPy** for numerical operations and preprocessing.
- **Pandas** for building the synthetic cohort and writing prediction files.
- **Scikit-learn** for patient-level splitting and classification metrics.
- **unittest** for the automated tests.
- **GitHub Actions** for running the tests and training examples when code is pushed or a pull request is opened.

OpenCV, TensorFlow, Keras, MONAI, SHAP, Grad-CAM, CNNs, LSTMs and Transformers are not used in this version.

## Preparing the data and checking the results

Patients are split into training, validation and test groups before the model is trained. All visits and visit-pairs from one patient stay in the same group, so the same synthetic patient does not appear in more than one partition.

The imputation values and scaling parameters are calculated from the training group only. Those values are then applied to the validation and test groups. The validation results are used to select the model checkpoint. The held-out test group is used for the final evaluation.

The code reports accuracy and macro-F1. Macro-F1 is calculated over all four stage labels, even when one of the labels is absent from a particular test split. The output also records how many test examples belong to each label.

The model creates probabilities for the four classes. These are outputs from a model trained on artificial data. They are useful for checking the software pipeline, but they do not show how the model would perform with real patients.

## Set up

Python 3.11 is the version used in the GitHub Actions workflow.

Clone the repository and create a virtual environment:

```bash
git clone https://github.com/sanafirdouse2323-glitch/multimodal-disease-progression-prototype-2.git
cd multimodal-disease-progression-prototype-2
python -m venv .venv
```

Activate the environment.

**Windows PowerShell**

```powershell
.venv\Scripts\Activate.ps1
```

**macOS or Linux**

```bash
source .venv/bin/activate
```

Install the packages. This command uses the CPU build of PyTorch, which is also used by the GitHub Actions workflow:

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu
```

For a GPU setup, use the PyTorch installation instructions for the CUDA or accelerator version on your machine: [PyTorch installation guide](https://pytorch.org/get-started/locally/).

## Run it

To check the pipeline with a small experiment:

```bash
python prototype.py --patients 40 --epochs 1 --batch-size 16
```

To run the larger example:

```bash
python prototype.py --patients 240 --epochs 12 --batch-size 32 --output-dir results
```

The script uses a GPU if PyTorch detects one. Otherwise, it runs on the CPU.

These are the available options:

| Option | Default | Meaning |
|---|---:|---|
| `--patients` | `240` | Number of synthetic patients |
| `--epochs` | `12` | Training epochs |
| `--batch-size` | `32` | Examples in each batch |
| `--learning-rate` | `0.001` | Adam learning rate |
| `--seed` | `42` | Random seed |
| `--output-dir` | `results` | Where the output files are saved |

## Files created by a run

After training, the output folder contains:

- `metrics.json` with the test accuracy, macro-F1, class counts, split sizes and training history.
- `test_predictions.csv` with the target stage, predicted stage and probability for each of the four stages.
- `model.pt` with the model weights, feature order, preprocessing values calculated from the training data, stage labels and run settings.

The output folder is created when the script runs. These files are not stored in Git.

A checkpoint from this project can be loaded with:

```python
from prototype import load_model_checkpoint

model, checkpoint = load_model_checkpoint("results/model.pt")
```

The loader checks that the feature order and stage labels in the checkpoint match the current code.

## Run the tests

Run the tests from the repository folder:

```bash
python -m unittest discover -s tests -v
```

The tests cover the synthetic cohort, next-visit target construction, patient splitting, the 20-feature model input, missing-value handling, the macro-F1 calculation and checkpoint saving and loading.

GitHub Actions runs these tests when code is pushed to `main` or a pull request targets `main`. It also runs the small training example, checks the generated prediction and metrics files, reloads the checkpoint, and runs the larger command shown above.

## What I still need to work on

There is quite a bit between this prototype and a proper study with medical data. In particular:

- The cohort and all measurements are synthetic. No real medical dataset has been connected.
- The image features are generated numbers. There is no scan loading, image preprocessing or image encoder.
- The model uses one visit at a time. It does not use the patient's full visit history or the time gap between visits.
- The target is the next recorded visit, which can be at different intervals for different patients. A fixed prediction horizon has not been defined.
- I have not compared this model with image-only, wearable-only or clinical-only baselines.
- Missing data needs more testing, including different missingness patterns and cases where a whole data group is unavailable.
- Causal treatment-effect estimation and fairness methods are not part of the code.
- The project has not been tested on an external dataset. Calibration, clinical review and clinical explainability have not been evaluated.

I keep a more detailed list of the current scope and remaining work in [docs/RESEARCH_SCOPE.md](docs/RESEARCH_SCOPE.md).

## Use of health data

This repository is public, so please do not add identifiable patient records, medical images, patient IDs or private cohort files to it. Real health data should only be used with the required permissions, ethics approval and secure storage arrangements.

This is a software and research prototype. It is not a medical device and should not be used to diagnose someone, recommend treatment or estimate an individual's prognosis.
