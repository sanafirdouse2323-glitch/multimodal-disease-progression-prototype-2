# Multimodal Disease Progression Prototype 2

I built this project to explore how information from medical images, wearable devices and clinical measurements could be used together when studying changes in a person's health over time.

This is an early software prototype. All patients, measurements and disease-stage labels are generated by the program. It does not use real patient records, medical scans or data from wearable devices. The results are only useful for checking the code and the experiment.

## What the program does

The program creates a sample group of 240 patients by default. Each patient has between two and four visits. The time between visits varies: 3, 6, 9 or 12 months.

For each visit, it generates 20 numerical values:

| Information group | Number of values | What is included |
|---|---:|---|
| Image-related features | 8 | Generated numbers; no image is loaded or processed |
| Wearable measurements | 6 | Generated summaries |
| Clinical information | 4 | Scaled age, a binary sex field and two generated lab values |
| Missing-data flags | 2 | Flags for missing image-related or wearable information |
| **Total** | **20** | |

The program also assigns each visit a stage from 0 to 3. These are made-up labels for this experiment. They are not part of a recognised medical staging system.

## How the model is built

I used Python and PyTorch to build a small neural network. It has a separate part for each information group:

- The image-related features go through one encoder.
- The wearable measurements go through a second encoder.
- The clinical values and missing-data flags go through a third encoder.

The three outputs are joined in a fusion layer. The network then makes two predictions:

1. The main output estimates the stage at the patient's next recorded visit.
2. An auxiliary output estimates the stage at the current visit during training.

For each training example, the model receives information from one visit and is asked to predict the stage recorded at the next visit. The current stage is used as an additional training target; it is not included among the input features.

The visits happen at different time intervals, but the model is not told how much time has passed between them. It also does not process the full sequence of a patient's visits. It is therefore a next-recorded-visit classification experiment, not a model that predicts a patient's condition at a fixed point in the future.

There is no image-processing network in this version. The image-related part uses eight generated numbers, not medical scans.

## Data split and evaluation

The program separates patients into training, validation and test groups. All visits belonging to one patient stay in the same group. This avoids putting visits from the same person in both training and test data.

The program calculates missing-value replacement values and scaling parameters from the training group only. It then applies those same values to the validation and test groups.

The validation results are used to choose the saved model. The final metrics are calculated on the held-out test group. The program reports:

- Accuracy
- Macro-F1
- Number of test examples in each of the four generated stages

The metrics describe performance on this generated dataset only. They do not tell us how the model would perform with patients.

## Set up

Python 3.11 is the version used in the GitHub Actions workflow.

Clone the repository:

```bash
git clone https://github.com/sanafirdouse2323-glitch/multimodal-disease-progression-prototype-2.git
cd multimodal-disease-progression-prototype-2
python -m venv .venv
```

Activate the environment.

**Windows PowerShell**

```powershell
.venv\Scripts\Activate.ps1
```

**macOS or Linux**

```bash
source .venv/bin/activate
```

Install the packages:

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu
```

The command above installs the CPU version of PyTorch, which is also used in the GitHub Actions workflow. For a GPU installation, follow the [PyTorch installation instructions](https://pytorch.org/get-started/locally/).

## Run the program

To run a short check:

```bash
python prototype.py --patients 40 --epochs 1 --batch-size 16
```

To run the larger example:

```bash
python prototype.py --patients 240 --epochs 12 --batch-size 32 --output-dir results
```

The program uses a GPU if PyTorch detects one. Otherwise, it runs on the CPU.

Available options:

| Option | Default | Description |
|---|---:|---|
| `--patients` | `240` | Number of generated patients |
| `--epochs` | `12` | Number of training epochs |
| `--batch-size` | `32` | Number of examples in each batch |
| `--learning-rate` | `0.001` | Learning rate for Adam |
| `--seed` | `42` | Random seed |
| `--output-dir` | `results` | Folder for output files |

## Files produced

After a run, the output folder contains:

- `metrics.json` — test metrics, class counts, split sizes and training history.
- `test_predictions.csv` — actual generated test labels, predicted labels and probabilities for the four stages.
- `model.pt` — model weights, feature order, preprocessing values, stage labels and run settings.

These files are created when the program runs and are not committed to the repository.

To load a saved model:

```python
from prototype import load_model_checkpoint

model, checkpoint = load_model_checkpoint("results/model.pt")
```

The loader checks that the saved feature order and stage labels match the current version of the code.

## Run the tests

From the repository folder, run:

```bash
python -m unittest discover -s tests -v
```

The tests check the generated patient data, next-visit target construction, patient-level splitting, the 20-feature input, missing-value handling, metric calculation, and saving and loading model checkpoints.

GitHub Actions runs the tests when code is pushed to `main` or when a pull request targets `main`. It also runs a short training example, checks the generated files and checkpoint, and runs the larger example shown above.

You can see the workflow results in the [Actions tab](https://github.com/sanafirdouse2323-glitch/multimodal-disease-progression-prototype-2/actions).

## What is not finished

There are several parts I have not added yet:

- The project uses generated data. It has not been connected to a real medical dataset.
- The image-related values are generated numbers. The program does not load, prepare or analyse medical scans.
- The model does not use a patient's full visit history or the time between visits.
- It predicts the next recorded visit, which may be months away. A fixed prediction period has not been defined.
- I have not compared the combined model with image-only, wearable-only or clinical-only models.
- Missing-data experiments need to cover more situations, including the loss of an entire information group.
- Treatment-effect estimation and fairness analysis are not included in this version.
- I have not assessed calibration, explanations or performance on an independent dataset.
- The generated stage labels are not a recognised measure of disease severity.

I have listed the current scope and further work in [docs/RESEARCH_SCOPE.md](docs/RESEARCH_SCOPE.md).

## Use of health data

Please do not add identifiable patient information, medical images, patient IDs or private dataset files to this public repository.

Any work with real health data would need the required permissions, ethics approval and secure storage. The dataset, prediction target, evaluation plan and clinical meaning of the measurements would also need to be agreed with the relevant research team.

This project is a coding and research exercise. It is not a medical device and must not be used to diagnose a condition, recommend treatment or predict an individual's health outcome.
