# Multimodal Disease Progression Prototype 2

I built this project to try out a small PyTorch model that combines different types of health-related data. The three groups in this version are image-derived features, wearable summaries and clinical measurements. I am using the project to work through the data preparation, model and evaluation steps for a disease-progression research idea.

At the moment, the experiment uses synthetic data generated by the Python script. It does not use real patient records or medical scans. The stage labels are also artificial. I have kept the experiment small so that the code can be run and checked without needing access to a medical dataset.

This repository is separate from my `multimodal-disease-progression-demo` project and from PACA++.

## What I have included

The script generates a synthetic cohort. Each patient has between two and four visits, with the time between visits varying between 3, 6, 9 and 12 months.

For each visit, it creates 20 input features:

| Feature group | Number of values | What they represent |
|---|---:|---|
| Image-derived | 8 | Simulated numerical values; no actual scan is read |
| Wearable | 6 | Simulated wearable summaries |
| Clinical/tabular | 4 | Scaled age, a binary sex field and two simulated lab values |
| Missingness indicators | 2 | Flags for missing image and wearable information |
| **Total** | **20** | |

Some clinical values can also be missing. The script records when the image or wearable group is absent and uses the missingness indicators as part of the model input.

The four stage labels are numbered 0 to 3. They are generated for this experiment and are not a recognised clinical staging system.

## How the prediction is made

For each patient, I pair a visit with that patient's next recorded visit. The model uses the current visit's 20 features to predict the stage label at the next observed visit. The current stage is also used as an auxiliary training target, but it is not included in the input feature list.

The network has a separate feed-forward encoder for each feature group. It combines the three encoded representations and produces two outputs:

- The main output predicts the next observed visit's stage.
- The auxiliary output predicts the current visit's stage during training.

The time between visits varies, but the elapsed time is **not** passed to the model. The model also does not process a sequence of earlier visits. Each training example contains one current-visit feature vector. So, this is a next-observed-visit classification experiment, not a fixed six- or twelve-month forecast and not yet a time-aware longitudinal model.

## Data preparation and evaluation

I split the cohort by patient, not by individual visit. All examples belonging to one patient stay in the same training, validation or test partition.

The imputation values and scaling parameters are calculated from the training partition only. I then use those same values for the validation and test partitions. The test partition is kept separate from model selection; the validation results are used to select the checkpoint.

The evaluation reports accuracy and macro F1. Macro F1 is calculated across all four defined stage labels, including a label that may not appear in a particular test split. The test output also records the number of examples belonging to each stage.

These metrics describe this synthetic experiment only. They should not be read as evidence that the model can predict disease progression in real patients.

## Files in this repository

- `prototype.py` — synthetic cohort generation, feature preparation, model definition, training, evaluation and checkpoint loading.
- `tests/test_prototype.py` — tests for the feature schema, forecast target construction, patient splitting, preprocessing, model inputs and outputs, metrics and checkpoint reload.
- `docs/RESEARCH_SCOPE.md` — what is implemented and what still needs research and development.
- `requirements.txt` — Python package requirements.
- `.github/workflows/tests.yml` — GitHub Actions workflow for tests and a small training run.

## Set up

Python 3.10 or later is recommended.

Clone the repository and create a virtual environment:

```bash
git clone https://github.com/sanafirdouse2323-glitch/multimodal-disease-progression-prototype-2.git
cd multimodal-disease-progression-prototype-2
python -m venv .venv
```

Activate it.

**Windows PowerShell**

```powershell
.venv\Scripts\Activate.ps1
```

**macOS or Linux**

```bash
source .venv/bin/activate
```

Install the packages:

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

For a CPU-only environment, the PyTorch CPU package index can also be used:

```bash
python -m pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu
```

For a machine using a GPU, install the PyTorch build that matches the machine's CUDA or accelerator setup, following the instructions on the official [PyTorch installation page](https://pytorch.org/get-started/locally/).

## Run the prototype

A small run that checks the training pipeline:

```bash
python prototype.py --patients 40 --epochs 1 --batch-size 16
```

A larger synthetic run:

```bash
python prototype.py --patients 240 --epochs 12 --batch-size 32 --output-dir results
```

The available command-line options are:

| Option | Default | Purpose |
|---|---:|---|
| `--patients` | `240` | Number of synthetic patients to generate |
| `--epochs` | `12` | Number of training epochs |
| `--batch-size` | `32` | Number of examples in each batch |
| `--learning-rate` | `0.001` | Adam optimizer learning rate |
| `--seed` | `42` | Random seed |
| `--output-dir` | `results` | Folder where the outputs are saved |

The script uses a GPU when PyTorch detects one; otherwise it runs on the CPU.

## Output files

After a successful run, the output folder contains:

- `metrics.json` — held-out accuracy, macro F1, class support, split sizes and training history.
- `test_predictions.csv` — target stage, predicted stage and the probability assigned to each of the four stages.
- `model.pt` — model weights, feature order, training-set preprocessing values, stage labels and run configuration.

The output folder is created when the script runs. These generated files are not committed to the repository.

A saved checkpoint can be loaded in Python with:

```python
from prototype import load_model_checkpoint

model, checkpoint = load_model_checkpoint("results/model.pt")
```

The loader checks that the saved feature order and stage labels match this version of the model.

## Run the tests

From the repository folder, run:

```bash
python -m unittest discover -s tests -v
```

The tests check more than whether the script imports. They check how the next-visit target is formed, whether patients stay in one data partition, the 20-feature model input, the handling of missing values, the four-label macro-F1 calculation and whether a saved checkpoint can be loaded again.

GitHub Actions runs the tests and a small training experiment when a change is pushed to `main` or a pull request targets `main`. It also checks that the run creates the expected files and that the saved predictions and checkpoint can be read.

## What still needs work

This is an early research prototype. There are important parts that I have not implemented yet:

- There is no real medical dataset in the repository. The patients, measurements and stage labels are synthetic.
- The image branch receives eight simulated numerical values. It does not load scans or extract image features.
- The model does not use the time gap between visits or a patient's earlier visit history.
- The prediction target is the next recorded visit. A clinically meaningful fixed forecast horizon has not been defined.
- There are no comparisons yet against unimodal models or established multimodal baselines.
- Missing-data behaviour has not been tested under different assumptions such as MCAR, MAR and MNAR, or against real missing-modality patterns.
- Causal treatment-effect estimation and fairness mitigation are not implemented.
- External validation, clinical assessment, calibration analysis and a clinical explainability evaluation have not been carried out.

I have described these points in more detail in [docs/RESEARCH_SCOPE.md](docs/RESEARCH_SCOPE.md).

## Data and clinical use

Please do not add identifiable patient information, medical scans, patient IDs or private cohort files to this public repository. Any use of real health data needs the appropriate permission, ethics review and secure data-handling arrangements.

This code is for research development and learning. It is not a medical device or a clinical decision-support system. It must not be used to diagnose a condition, recommend treatment or estimate an individual's actual prognosis.
